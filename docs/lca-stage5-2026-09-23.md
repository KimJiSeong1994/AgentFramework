# lca 5단계(모델) 1차 슬라이스: 같은 벤치로 모델 비교

- 일자: 2026-09-23
- 근거: `docs/agent-framework-review-2026-09-22.md` §6 로드맵 5단계("`qwen3.6:35b-a3b-coding-mtp` 동일 벤치(툴 신뢰성·MTP 수락률·프리픽스 캐시)", 완료 기준 "툴 오류율·SWE류 과제 비교표")
- 커밋하지 않음.

## 1. 범위와 제약

- e2e 두 스크립트에 모델 오버라이드를 넣었다: `scripts/lca-e2e-data.sh --model ollama/<id>`, `LCA_E2E_MODEL=ollama/<id> scripts/lca-e2e.sh`. 모델은 사용자 `opencode.jsonc`의 `provider.ollama.models`에 있어야 한다(없으면 즉시 종료). 나머지 격리(XDG, 스크래치 설정, 플러그인 per-project)는 그대로.
- **qwen3.6:35b-a3b는 로컬에 없다**(`ollama list`: gemma4 26B MoE·31B MLX·31B GGUF, llama3.2 3B, gpt-oss). 20GB 급 다운로드는 사용자 결정 사항이라 받지 않았고, 대신 이미 있는 `gemma4:31b-mlx`(dense 31B, MLX+MTP, thinking off)를 26B MoE 기본값과 같은 벤치로 비교했다. qwen이 준비되면 같은 두 명령으로 표를 채운다.
- 단일 Ollama 슬롯이므로 31B 로드는 26B를 내리고, 벤치 후 첫 26B 요청이 다시 로드한다(사용자 TUI 세션은 살아 있고 한 번 느려질 뿐).

| 원장 | 3/3 done, 각 1회 | 3/3 done, 각 1회, 리뷰 accept×3, verify pass×3 |

| 판정 | E01~E14 PASS | E01~E14 중 E07만 FAIL(위 집계 차이), 나머지 PASS |

해석:
- **정확도는 두 벤치 모두 동률**(데이터 10/10, 코딩 3/3 + 리뷰 accept). 이 벤치들은 26B가 이미 만점이라 31B의 품질 이점을 드러내지 못한다. 더 어려운 픽스처(tier-3 질의, 다파일 리팩터링)가 있어야 차이가 보인다.
- **속도는 26B MoE가 2.5~5.6배 빠르다**. 프리픽스 캐시 계약(≤8K, thinking off, 반복 0)은 모델과 무관하게 지켜졌다(E03·E04·E08·E10·E11 PASS).
- E07의 main 캐시 미스 0은 MLX 러너가 토큰 통계를 다르게 보고하는 문제로 보이며, e2e의 "main == 1" 기대는 GGUF 러너 기준이다. 러너별 허용치(0~1)로 바꾸는 것이 맞다(미수정, 기록만).
- 결론: 기본 모델은 26B MoE 유지. 31B는 품질이 필요한 세션 단위 전환용(§5.5의 "세션 단위 전환만"과 일치).

## 3. qwen3.6:35b-a3b-coding-mtp-q4_K_M (같은 날 오후, 22GB pull 후)

### 3.1 1차 실행 (수정 전) — 프레임워크 결함 2건 발견

| 벤치 | 결과 |
|---|---|
| 데이터 10문항 | **7/10** (tier-1 5/7). TEXT-005는 `resolve_semantics`를 부르지 않고 행 목록을 답함(집계 아님). HPAI-MAP-001·003은 **db_query를 한 번도 부르지 않고 `RESULT: [(3,)]`를 지어냈다**(resolve만 호출). 질의당 2.7~5.5K 토큰, 13~30초 |
| 코딩 ulw3 | 3/3 done, 리뷰 accept×3, 112초, E07 PASS. **E10 FAIL: 자식 세션에 reasoning 파트 12개** |

원인과 수정:
1. `chat.params`의 thinking-off가 **Gemma 전용**(`isGemmaOnOllama`)이어서 qwen 워커/리뷰어/분석가는 thinking ON으로 돌았다 → Ollama가 서빙하는 모든 모델에 `reasoningEffort: none`을 적용하도록 바꿈(`isOnOllama`; Ollama는 thinking 모델마다 `reasoning_effort`를 `think` 스위치로 매핑하고 나머지는 무시).
2. e2e의 `SQL:` 블록 정규식이 코드펜스 없는 답을 못 잡았다(백틱 2개를 요구). Gemma는 항상 db_query를 불러 마지막 호출 인자로 폴백됐지만, qwen처럼 db_query를 건너뛴 답은 "SQL 없음"으로 집계됐다 → 정규식 수정. 이 결함은 **결과 판정에만** 영향(정답 SQL을 쓰고 실행을 안 한 케이스는 재실행하면 맞을 수 있음).
3. "db_query 없이 RESULT를 지어냄"은 모델 결함이며, 3단계 파이프라인이 RESULT를 신뢰하지 않고 SQL을 재실행하는 이유 그 자체다. 직접 호출 e2e에서는 D01이 재실행으로 판정하므로 결과는 살리되, 별도 지표(`db_query` 0회)로 드러내는 것이 맞다 — 미구현, 기록만.

### 3.2 2차 실행 (수정 후)

| 벤치 | 26B MoE (기본) | 31B-mlx | **qwen3.6:35b-a3b-coding-mtp-q4_K_M** |
|---|---|---|---|
| 데이터 정답 | 10/10 | 10/10 | **7/10** (tier-1 6/7) |
| 데이터 질의당 토큰 / 벽시계 | 2.1~4.6K / 7~19초 | 1.2~4.6K / 19~70초 | 2.3~4.0K / 7~15초 (MAP-002만 10.5K·66초·툴 8회로 D02·D03 초과) |
| 데이터 판정 | D01~D07 PASS | PASS | D01 PASS(≥6), D02·D03 FAIL(MAP-002) |
| 코딩 ulw3 | 3/3, 64초, E01~E14 PASS | 3/3, 361초, E07만 집계 차이 | **3/3, 65초, E01~E14 PASS** (프리픽스 main 5,053 / 워커 3,891 / 리뷰어 2,113) |

데이터 실패 3건의 내용(재실행 판정, SQL은 하네스가 실행):
- MAP-001: SQL은 맞게 썼지만 헤더를 `{{ sql }}:`로 출력(템플릿 잔재)해 계약을 벗어났고, **db_query 없이 RESULT 표를 지어냈다**.
- HPAI-MAP-002: resolve 결과를 오독해 "1392는 야생조류 발생 건이라 산출 불가"라고 **db_query 없이 거절**(지어낸 근거).
- MAP-002: 툴 8회·10.5K 토큰·66초 끝에 오답(방문 횟수 4/3/3 — 위험 차량 조인 누락 추정).

해석:
- **코딩 위임은 qwen이 26B와 동급**(3/3, 65초 vs 64초, 프리픽스 계약 유지). thinking을 끄자 112초 → 65초, reasoning 파트 12 → 0.
- **데이터 계약 준수는 26B가 낫다.** qwen은 10문항 중 3문항에서 SQL을 실행하지 않고 결과를 지어내거나 거절했다(1차 실행에서도 2문항). 이것이 3단계 파이프라인이 `RESULT:`를 신뢰하지 않고 SQL을 재실행하며, 위임 경로에서는 SQL 없는 답을 재시도시키는 이유다. 직접 호출 e2e는 그 보호가 없으므로 그대로 실패로 드러난다.
- 기본 모델은 26B MoE 유지. qwen은 코딩 전용 세션 후보로 둘 만하며, 데이터 에이전트로는 부적합(계약 이탈).

## 4. 남은 것

- MTP 수락률은 Ollama 로그(`OLLAMA_DEBUG`)에서 따로 봐야 하며 이 벤치는 잡지 않는다.
- e2e에 D10("`SQL:` 블록은 있는데 db_query 호출 0회 → 결과를 지어냄")을 추가해 qwen류의 집행 생략이 실패로 잡힌다(`db_calls` 컬럼). 툴 인자 오류 횟수는 아직 세지 않는다.
