# otter 기능 고도화 검토 — 2026-10-20

기준: master `9e0a130`. 모든 진단은 코드·로컬 상태로 확인한 사실이며 위치를 적었다.

## 요약

1. **핵심 가치 "실행 이력 → 자산" 루프가 실제 사용 경로에서 끊겨 있다.** 지금 주 경로인 CLI 엔진(codex/claude/local)은 도구 결과를 이력 DB에 쓰지 않고, 위키 캡처는 수동이며 마지막 갱신이 10/2다. 가장 먼저 고칠 것.
2. **방금 켠 직접 실행은 동작하지만 거칠다.** 한 응답에 도구 1개, 턴당 24회, 작은 입력 예산, 동작마다 승인, 되돌리기 없음.
3. **엔지니어링 기반이 약하다.** CI가 없고, 전체 테스트가 15분을 넘으며, master에 실패하는 테스트가 1개 있다.

## 1. 이력 → 자산 루프 (최우선)

| 진단 | 근거 |
|---|---|
| CLI 엔진은 `tool-outcomes.sqlite`에 기록하지 않음. 기록 경로는 OpenCode 훅뿐 | `hooks/event.ts:186` 만 `recordToolOutcome` 호출. 이 저장소 DB 파일 없음, 행 0개 |
| 위키 캡처는 수동 스크립트 | `scripts/otter-wiki.ts`: "capture is explicit, manual" |
| 위키 리포트가 오래됨 | `knowledge/wiki/reports/*.md` 10/2 이후 갱신 없음 |
| 가장 풍부한 이력(세션 기록: 요청·답변·계획·승인·명령 종료코드)이 위키 입력이 아님 | `captureWiki`는 tool-outcomes·routing·skill observation만 읽음 (`wiki/wiki.ts:631`) |

제안
- **1-A. CLI 도구 결과 기록**: 호스트 활동(`tool-finished`)을 메타데이터만 `tool-outcomes.sqlite`에 기록. 인자·본문 미저장 원칙 유지. 작업량 소.
- **1-B. 세션 다이제스트**: 세션 종료·`/new` 시 결정적 요약 1건 생성(요청 요지, 바뀐 파일, 실행 명령과 종료코드, 승인/거부 수, 결과) → 불변 원본으로 저장. 모델 호출 없음.
- **1-C. 자동 캡처**: `wiki.auto_capture`(기본 on) — 세션 종료 시 캡처 실행, 실패해도 종료를 막지 않음.
- **1-D. 다음 작업에서 회수**: 턴 시작 시 기존 memory prefetch에 "비슷한 과거 세션" 회수 추가. 같은 명령이 반복 실패한 기록은 "알려진 함정" 페이지로.
- 지표: 캡처된 세션 비율, 회수가 답변에 쓰인 비율.

## 2. 직접 실행 품질

| 진단 | 근거 |
|---|---|
| 응답당 도구 1개만 실행 → 왕복 과다 | `cli-host.ts:1033` "Only the first tool call in a reply runs" |
| 턴당 도구 24회 상한, 초과 시 실패 | `MAX_TOOL_ROUNDS = 24` |
| 입력 예산이 작음(대형 컨텍스트 모델 대비) | main 8192 / vendor 16384 토큰, 대화창 24,000자 (`cli-host.ts:44-49`, `plan-conversation.ts:11`) |
| 편집은 정확히 1회 일치 문자열 치환만 | `cli-tools.ts` edit |
| 동작마다 승인 → 피로 | `chat-actions.ts` |
| 대화 중 수정은 체크아웃에 직접 반영, 되돌리기 없음 | 계획 경로만 작업 트리 사용 |
| 진행 표시가 여전히 "Planning…" | `cli-progress.ts:177` |

제안
- **2-A. 읽기 도구 묶음 실행**: 한 응답의 read/grep/glob 여러 개를 순서대로 실행(쓰기·명령은 계속 1개씩 승인).
- **2-B. 체크포인트와 `/undo`**: 턴의 첫 쓰기 전에 변경 대상 파일 스냅샷 → `/undo`로 해당 턴 수정 되돌림.
- **2-C. 승인 피로 줄이기**: 읽기 전용 명령 안전 목록(`git status/diff/log`, `ls`, `cat` 등) 자동 실행, "이 턴 동안 이 폴더 수정 허용" 옵션, 여러 파일 수정 묶음 diff 1회 승인(`multiedit`).
- **2-D. 엔진별 예산**: claude/codex는 예산 상향, 상한 도달 시 실패 대신 "계속할까요?".
- **2-E. 표시 정리**: 실행 모드에서 "Planning" → "Working".

## 3. 엔진·콤보

- **3-A. 엔진 장애 시 전환 제안**: 로그인 만료·한도 초과·CLI 실패 시 "다른 엔진으로 이어가기" 한 번에(대화 이어짐). 지금은 오류 안내만.
- **3-B. 사용량 표시**: 세션별 역할·모델별 시간/호출 수를 `/status`와 상태줄에. 콤보 효과 판단 근거.
- **3-C. 콤보 효과 이력화**: 콤보별 작업 성공률·재시도 수를 1-B 다이제스트에 남겨 추천 프리셋 근거로.

## 4. 스킬·의도 라우팅

- **4-A. 스킬 효과 측정**: 스킬 사용 턴 뒤의 결과(테스트 통과, 거부, 재시도)를 다이제스트에 연결 → 자동 스킬 후보 순위에 반영. 1번 루프 위에서만 가능.
- **4-B. 의도 라우팅 → 모드 연결**: "구현" 의도는 ask 실행으로, 큰 변경은 `/plan` 제안으로 자연스럽게 연결.

## 5. 엔지니어링 기반

| 진단 | 근거 |
|---|---|
| CI 없음 | `.github/workflows` 없음. 최근 PR 전부 로컬 테스트로만 병합 |
| 전체 테스트 15분 초과 | 161개 파일, 단일 실행 시간 초과 |
| master에 실패 테스트 1개 | `tui-skill-completion` "skills appear only where…" |
| Windows/WSL 실기 미검증 | install.ps1·otter-wsl은 가짜 wsl.exe로만 확인 |
| 업데이트 알림이 "무엇이 바뀌었는지" 모름 | 커밋 비교만 (`update-check.ts`) |

제안
- **5-A. GitHub Actions**: macOS·Ubuntu에서 테스트 샤딩(4~6개) + 타입체크 + PTY 하네스. PR 병합 조건으로.
- **5-B. 실패 테스트 수정**.
- **5-C. Windows 잡**: windows 러너에서 install.ps1 파싱·시뮬레이션, 가능하면 WSL 스모크.
- **5-D. 릴리스 태그·변경 요약**: 업데이트 알림에 주요 변경 3줄.
