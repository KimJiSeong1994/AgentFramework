# lca 4단계(진화·팀) 1차 슬라이스: 온톨로지 진화 배치

- 일자: 2026-09-23
- 근거: `docs/agent-framework-review-2026-09-22.md` §5.6 진화 행("rolling_trajectory, 검증셋 10~15문항, 라운드 2~3, LLM Judge = 같은 Gemma, Accept돼도 set_active_version은 사람 승인 후, 야간 헤드리스"), §6 로드맵 4단계("진화 1런 무인 완료")
- 커밋하지 않음. 3단계 2차 슬라이스(main→analyst 위임)는 `docs/lca-stage3-2026-09-23.md` §6.

## 1. 사전 조사 (벤더 EvoOntology 코어)

- 벤더 패키지는 **결정적 코어만** 있고 업스트림 SKILL.md(빌드/진화 지능)는 없다. 호스트 모델이 내용(가설·후보 레코드·평가 수치)을 공급하고 코어는 라이프사이클 규칙(예산·게이트·상태 전이)을 강제한다.
- 진화 API(Python, MCP 없이 직접 호출 가능): `EvolutionSession.start_run(parent, max_rounds, acceptance)` → `begin_round(hypothesis, candidate)` → `record_evaluation(subject, {metrics, cases, gate_input})` → `accept()` 또는 `record_round(decision="reject")` → 예산 소진 시 `incomplete`. 후보 버전은 `SemanticStore.save_version(ws, name, records)`로 5개 파일을 통째로 쓴다(델타 API 없음).
- 게이트 `gate_input.protocol`: `ground_truth`(parent/candidate 점수 쌍 + case_ids, 평균 비교, 결정적) 또는 `llm_judge`(verdicts, critical_error 0 + candidate 승 > parent 승). **`accept()`는 발행과 동시에 `active.json`을 바꾼다** — "사람 승인 후 활성화" 요구는 코어에 없다.
- `rolling_trajectory` 모드의 유일한 분기는 workload 준비(trajectories에서 질문을 모음)이고 진화 루프 자체는 모드와 무관.

## 2. 구현 (`scripts/lca-evo-evolve.py`, stdlib)

| 단계 | 내용 |
|---|---|
| 부모 평가 | `scripts/lca-e2e-data.sh --evo-workspace <ws> --tier 2`: 문항마다 `data-analyst`가 답하고 하네스가 SQL을 재실행해 `queries.jsonl`의 기대 결과와 비교 → 케이스 점수 1/0. e2e가 `resolve_semantics` 응답에서 **미해결 mention**을 뽑아 결과 TSV에 기록(신설 컬럼). 케이스마다 `trajectories/e2e-<stamp>-<id>.json` 추가 |
| 제안 | `ontology-evolver` 에이전트(신설, `mode: all`, 툴 0, steps 2, 출력 4,096, 프리픽스는 자기 것만). 입력 = 현재 용어(id·이름·별칭)·제약(id·키워드·규칙)·실패 케이스(질문, 미해결 mention, 작성된 SQL, 틀린 이유). **기대 답은 주지 않는다.** 출력 = JSON 패치 `{hypothesis, aliases[], terms[], constraints[]}` |
| 패치 검증 (코드) | 추가만 허용: 기존 term의 별칭 추가(중복 무시), 새 term(`t-<slug>`, 이름 중복 금지, 정의 필수), 새 constraint(`c-<slug>`, target은 기존 term/mapping). 삭제·개명 불가. 빈 패치·JSON 불량은 라운드 reject로 기록 |
| 후보 평가 | `save_version(candidate_rN_<stamp>)` → `validate_semantics` → 임시 워크스페이스 사본(active = 후보)에서 같은 e2e → 점수 |
| 게이트 | `ground_truth`: 후보 합 > 부모 합 **이고** 케이스별 퇴행 0 (코어 게이트보다 엄격). 통과 시 `accept()`가 `ontology_v(N+1)`로 발행 → 즉시 `set_active(parent)`로 되돌림 → `evolution/run_N/proposal.md`(가설·패치·케이스 표·승인 명령). 불통과 시 `record_round(reject)` 후 다음 라운드에 이전 가설·결과를 넣어 재제안 |
| 승인 | `python3 scripts/lca-evo-evolve.py --workspace <ws> --activate ontology_vN` (validate 후 active.json만 바꿈). git 관리 워크스페이스에서는 새 버전 디렉터리 + proposal.md가 PR diff |
| 테스트 | `--self-test`(패치 검증 8종, 모델 없음) → doctor D11e. `--dry-run`은 부모 평가 + 프롬프트 출력까지 |

판정자가 LLM이 아니라 코드인 이유: 픽스처에 정답이 있으므로(`result_match`). 운영 질문(정답 없음)에는 §5.6대로 `llm_judge` 프로토콜(같은 Gemma가 parent/candidate 답을 익명 비교)을 붙여야 하고, 이 드라이버의 `record_evaluation` 호출부만 바뀐다.

## 4. 2차 슬라이스 (같은 날): 정답 없는 질문용 `llm_judge`, 야간 스케줄

| 구현 | 내용 |
|---|---|
| `--questions F.jsonl` / `--no-ground-truth` / `--protocol` | `expected`가 없는 질문 파일이면 e2e가 match=-1로 SQL과 첫 5행만 기록(신설 `rows` 컬럼, D01은 "정답 없음"으로 PASS). 프로토콜 기본값: 전 문항에 `expected`가 있으면 `ground_truth`, 아니면 `llm_judge` |
| 실패 케이스 정의(정답 없음) | 미해결 mention이 있거나, SQL 오류·SQL 없음·빈 결과인 케이스. 이것이 evolver의 입력이 된다(정답을 모르는 운영 질문에서 온톨로지 공백을 찾는 유일한 신호) |
| `answer-judge` 에이전트(신설, 툴 0, steps 2, 출력 512) | 케이스마다 질문 + 답 A/B(SQL + 첫 행). `EvaluationGate.anonymize`가 부모/후보를 무작위로 A/B에 배정하고 `decode`가 되돌린다 — 판정자는 어느 쪽이 후보인지 모른다. 출력 `{"winner": "A"|"B"|"tie", "critical_error": "A"|"B"|null, "reason"}`; 파싱 불가는 tie |
| 게이트 | `EvaluationGate.decide_judge`: 후보 치명 오류 0 **이고** 후보 승 > 부모 승. 코어 규칙 그대로 |
| `scripts/lca-evo-nightly.sh` | `EvolutionTrigger.check()`(기본: 새 궤적 30건 또는 7일)가 due일 때만 드라이버 실행(`--force`로 생략), 잠금 디렉터리, Ollama 헬스체크, `~/.cache/lca/evo/evo-<stamp>.log`. `scripts/launchd/com.lca.evo-nightly.plist` 템플릿(03:30, 설치는 사람이) |

### 4.1 실측: 정답을 지운 픽스처 질문 10개, llm_judge, 1라운드

| 단계 | 결과 |
|---|---|
| 부모 평가 | 10문항 답 수집(match=-1), 미해결 mention 있는 케이스 6개 → evolver 입력 |
| 라운드 1 패치 | 별칭: t-farm `가금 농장/산란계 농장/오리 농장`, t-outbreak-wild `야생조류 검출 건수`, t-visit `농장 방문 동선`, t-purpose `사료운반 차량`; 제약 `c-livestock-place-combination`(축종+농장 조합 규칙). 정답 없이도 evolver는 3단계에서 사람이 넣었던 별칭 계열을 다시 찾아냈다 |
| 판정 (10건, 익명 A/B) | 후보 승 3(HPAI-MAP-002, HPAI-MAP-003, MAP-001), 부모 승 1(TEXT-004), 동점 6, **후보 치명 오류 1**(TEXT-004: 후보 SQL이 `h.place_type` 컬럼을 잘못 참조) |
| 게이트 | `decide_judge`: 치명 오류 ≠ 0 → **REJECT**, 런 incomplete(예산 1라운드). 무인 종료, 5분 4초 |

판정 품질(정답과 대조):
- 판정자는 HPAI-MAP-002에서 **가금 축종 필터를 "불필요한 필터"라 보고 그것을 뺀 답을 이겼다고 했고**, HPAI-MAP-003에서 **당일 포함(BETWEEN)을 단점으로 봤다**. 둘 다 정답과 반대다. 26B 판정자는 도메인 관례(가금의 정의, 창 포함)를 모르면 "더 단순한 SQL"을 선호한다.
- TEXT-004의 치명 오류 판정은 옳았고(후보가 없는 컬럼 사용), 코어의 "치명 오류 0" 규칙이 잘못된 승리 2건을 무효화했다. 즉 이번 런에서 REJECT는 결과적으로 맞았지만 승패 집계는 신뢰할 수 없다.
- 결론: 정답 없는 운영 질문에서는 (a) 판정자 프롬프트에 온톨로지의 **제약(관례) 목록을 함께 주고** (b) 판정 2회(A/B 순서 교체) 일치만 인정하는 식의 보강이 필요하다. 다음 슬라이스 항목. 이 픽스처에서는 ground_truth 프로토콜이 정본이다.
- SQL이 긴 문항(MAP-002)에서 판정 프롬프트가 SQL을 700자에서 잘라 "둘 다 잘렸다"는 판정이 나왔다 → 1,500자로 늘림(런 후 수정).

## 5. 3차 슬라이스 (같은 날): 워크트리 격리, 판정자 보강

### 5.1 태스크별 git 워크트리 (`delegate.worktree`, 기본 false)

- 사전 확인: SDK v1/v2의 `session.create`/`session.prompt`가 `query.directory`를 받고, 서버가 요청 단위로 디렉터리를 바꾼다(1.18.32 실측: `GET /file/content?directory=<wt>`가 워크트리의 파일을 읽고 `POST /session?directory=`로 만든 세션의 `directory`가 워크트리). 따라서 자식 세션의 툴이 다른 디렉터리에서 돌 수 있다 — 이것이 설계 §5.5 "워크트리 격리는 옵션"의 전제였다.
- `src/orchestration/worktree.ts`: `<state root>/worktrees/<session>/<task>`에 `git worktree add --detach HEAD` → main의 미커밋 추적 변경(`git diff HEAD`, binary) 적용 + 미추적·비무시 파일 복사(`diff_exclude` 제외) → 생성 시점 트리를 기준으로 기록. 태스크 채택 시 `merge()`가 워크트리의 누적 diff를 패치로 만들어 main에 `git apply --check` 후 적용; 안 맞으면 태스크 failed(`blocked` 사유) + 패치를 `.lca/handoffs/<session>/task-N.patch`에 보관. 실패·취소 태스크의 워크트리는 그냥 버린다(main은 그 변경을 본 적이 없다).
- 큐: 스냅샷·보호파일 복원·verify(cwd)·자식 세션(`directory`)이 모두 워크트리를 가리키고, 원장/handoff는 그대로 main 기준. 커밋이 없는 저장소는 in-place로 폴백.
- 단위 테스트 6개(생성 상태, 병합, 충돌, 폴백, 큐 경로 2종) → 총 262. 실 e2e: `scripts/lca-e2e.sh --fixture ulw3 --worktree` → 원장 3/3 done(각 1회), verify pass×3, 리뷰 accept×3, 로그에 `task worktree`/`task worktree merged` 3쌍, main 작업 디렉터리에서 `pytest` 10개 통과(병합 확인), 벽시계 88초(in-place 64초). **E07 FAIL: 워커 캐시 미스 3(기대 ≤1), main 2** — 워커 세션이 각자 다른 디렉터리에 바인딩되면 OpenCode가 시스템 프롬프트에 넣는 작업 디렉터리 정보가 달라져 워커 프리픽스가 태스크마다 새로 프리필된다. 즉 **격리의 대가는 태스크당 워커 프리필 1회(≈3.4K 토큰, 약 5초)**. 기본값 false를 유지하고, 사용자가 작업 중인 저장소에서 무인 위임을 돌릴 때(충돌 보호가 필요할 때)만 켜는 옵션으로 둔다. E07 기준은 워크트리 모드에서 "워커 미스 ≤ 태스크 수"로 완화하지 않았다(모드 차이를 숨기지 않으려고).

### 5.2 판정자 보강 (llm_judge)

- 판정 프롬프트에 온톨로지 제약(`severity != info`)을 "도메인 관례"로 함께 준다(4.1의 오판 2건은 관례를 몰라서였다).
- 케이스마다 A/B를 바꿔 2회 판정: 승자는 두 번이 일치할 때만, 치명 오류는 한 번이라도 후보에 찍히면 인정(부모 보호 쪽으로 보수적). 불일치는 tie로 기록하고 사유에 남긴다. `--self-test`에 포함.
- 재측정(같은 퇴화 픽스처, 정답 제거, 1라운드): 판정 후보 승 2 / 부모 승 0 / 동점 8 / 치명 오류 0 → **ACCEPT**, `ontology_v1` 발행(active 유지). 교차 2회로 3건이 "passes disagree → tie"가 됐고(HPAI-MAP-001, MAP-001, MAP-002), HPAI-MAP-002는 이번엔 판정 사유가 축종 관례(json_extract 조회)를 근거로 후보를 골랐다 — 관례 주입이 4.1의 오판 방향을 뒤집었다. 남은 잡음: e2e 결과 TSV가 SQL을 400자로 잘라 긴 질의(MAP-002)에서 "잘린 SQL" 판정이 나왔다 → 2,000자로 늘림(런 후 수정).
- 여전히 단일 런 표본이며, 정답이 있는 픽스처에서는 ground_truth가 정본이다. llm_judge는 운영 질문(정답 없음)에서 "치명 오류 0 + 교차 일치 승"만 믿는 보수적 게이트로 쓴다.

## 6. `OLLAMA_NUM_PARALLEL=2` 검증 (§5.5의 "슬롯 1 = 메인 캐시, 슬롯 2 = 워커 캐시")

사용자 서버(11434, NUM_PARALLEL=1)는 건드리지 않고 같은 모델 저장소로 두 번째 인스턴스(11435, `OLLAMA_NUM_PARALLEL=2`, ctx 16K)를 띄워 `scripts/lca-np-probe.py`로 측정했다: 서로 다른 ≈7.3K 토큰 프리픽스 A·B를 A A B A B A 순서로 보내고 프리필 시간을 본다(`prompt_eval_count`는 캐시 히트여도 전체 토큰 수를 보고하므로 시간이 신호).

| 서버 | 1 A | 2 A | 3 B | 4 A | 5 B | 6 A |
|---|---|---|---|---|---|---|
| NUM_PARALLEL=2 | 9.97초 | 0.04초 | 10.0초 | **0.05초** | 0.05초 | 0.04초 |
| NUM_PARALLEL=1 (사용자 서버) | 10.4초 | 0.06초 | 9.9초 | **0.08초** | 0.13초 | 0.08초 |

- **결론: 슬롯을 2개로 늘릴 필요가 없다.** Ollama 0.34.2의 llama-server는 슬롯이 비면 그 KV를 호스트 메모리의 프롬프트 캐시에 저장하고(로그: `idle slots will be saved to prompt cache upon starting a new task`) 같은 프리픽스가 오면 복원한다. 단일 슬롯에서도 A·B가 번갈아 와도 둘 다 0.1초 안에 복원됐다. 2단계 설계가 걱정한 "워커 프리필이 메인 캐시를 밀어낸다"는 이 버전에서는 일어나지 않으며, ulw3 e2e의 "main 미스 1, 워커 미스 1"이 그 증거였다.
- NUM_PARALLEL=2 자체는 동작한다: `n_slots = 2`, MTP 드래프트(`draft-mtp`) 초기화 정상. 대신 슬롯당 컨텍스트가 절반(`n_ctx_slot = ctx/2`)이 되므로 얻는 것 없이 잃기만 한다. `scripts/ollama-env.sh`의 `OLLAMA_NUM_PARALLEL=1` 유지.
- 리뷰어 세션이 매번 "미스"로 집계되는 것(E07 보고 항목)은 리뷰 프롬프트 본문(diff)이 매번 달라 공유 프리픽스가 1.7K뿐이기 때문이고, 캐시 격리 문제가 아니다.

## 7. 남은 것 (4단계 나머지)

- HUD: OpenCode 1.18.32 플러그인 타입에 `tui?: never`로 TUI 슬롯이 없다(§5.7의 `sidebar_content`는 이 버전에서 불가). 진행 신호는 자식 세션 제목(`lca task N` / `lca data N`)뿐.
