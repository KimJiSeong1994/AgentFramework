# lca 3단계(데이터 레이어) 1차 슬라이스 구현 결과

- 일자: 2026-09-23
- 근거 문서: `docs/agent-framework-review-2026-09-22.md` §5.2 (data-analyst/data-verifier), §5.3 (db_query/schema_lookup, evo-semantic MCP), §5.6 (EvoOntology 수용 결정), §6 로드맵 3단계
- 완료 기준(§6): "프로젝트의 대표 질의 세트를 온톨로지 경유로 재현, 질의당 ≤ 10K 토큰"
- 커밋하지 않음.

## 1. 사전 조사에서 확정한 사실 (조사 에이전트, 증거는 스크래치 노트)

- 대상 DB는 **PostgreSQL 16 + PostGIS**의 원격 운영 서버이고 프로젝트가 쓰던 자격은 **superuser**였다. 원천 테이블은 같은 호스트의 다른 DB에만 있어 **오프라인 재현 원천이 없다** → e2e는 운영 DB에 붙이지 않고 합성 sqlite 픽스처를 쓴다.
- 프로젝트의 대표 질의는 10문항(TEXT 5, MAP 3, HPAI-MAP 3). PostGIS 2문항(`ST_DWithin`), jsonb 속성 조회, 지역명 약칭, 시 단위 LIKE 같은 값 규칙이 정답 SQL의 핵심이다.
- EvoOntology(MIT, stdlib 전용, Python ≥3.10)는 3.13에서 159개 테스트 통과. MCP는 **자체 구현 stdio JSON-RPC**, 툴 29개(시맨틱 2 + 라이프사이클/진화 27). **DB를 읽지 않는 순수 시맨틱 레이어**이고 온톨로지는 `versions/ontology_vN/{terms,mappings,relations,constraints,evidence}.json`. LLM Judge 호출은 코어에 없고 호스트가 판정을 넣는다.
- OpenCode 1.18.32: 플러그인 `config` 훅으로 `config.mcp`를 주입할 수 있고(`opencode mcp list`로 확인), MCP 툴 이름은 `<server>_<tool>`, 에이전트 `permission`으로 가시성을 좁힐 수 있다(마지막 매칭 규칙 우선). `opencode debug agent` 출력에는 MCP 툴이 나오지 않는다(요청 시점에 붙음).

## 2. 구현 범위 (1차 슬라이스)

| 구현 | 위치 |
|---|---|
| `db_query(sql, max_rows?)`: SELECT/WITH 1문만(가드 `data/guard.ts`), sqlite는 python 헬퍼(`?mode=ro` + SELECT/READ 전용 authorizer + 진행 핸들러 타임아웃 + `dist_m()` 하버사인), postgres는 `psql` 서브프로세스(`BEGIN READ ONLY; SET LOCAL statement_timeout`)에 **loopback 전용**(`data.pg_allow_remote`로만 해제), DSN은 환경변수만. 결과는 행/셀/토큰 상한 + 힌트 줄, 세션당 호출 상한 | `framework/src/data/{guard,format,sqlite,sqlite_query.py,postgres,schema}.ts`, `tools/db-query.ts` |
| `schema_lookup(table?)`: 정적 JSON(`data/schema.json`)에서 테이블 1개(≤600 est. tokens) 또는 목록. 카탈로그 덤프 없음 | `tools/schema-lookup.ts`, 생성기 `scripts/lca-schema-extract.py`(Postgres DDL의 CREATE TABLE/COMMENT/ENUM/CHECK 파싱) |
| EvoOntology 코어 동봉(MIT, `framework/vendor/evoontology`), config 훅이 `config.mcp["evo-semantic"]`(stdio, 벤더 서버, 워크스페이스 `data.evo.workspace`)를 주입. **`browse_semantics`/`resolve_semantics`만** `data-analyst`에 노출, 나머지 27개와 다른 에이전트는 `evo-semantic_*: deny` | `hooks/config.ts` |
| 에이전트 `data-analyst`(`mode: all`, 툴 4개: db_query/schema_lookup/browse/resolve, 나머지 전부 deny, steps 12, thinking OFF, 출력 2,048), `data-verifier`(정의만, 툴 없음), `data` 모드 접미(≤300자, 키워드 data mode/데이터 모드/질의 모드) | `agents/prompts.ts`, `modes/*` |
| 픽스처 `scripts/fixtures/data-vv/`: 6테이블 sqlite(합성 169장소/60차량/588+방문/43+40 발생), `data/schema.json`, `queries.jsonl`(10문항 + sqlite 정답 SQL + 기대 결과), **코드 생성 온톨로지 v0**(용어 15·매핑 15·관계 6·제약 7·근거 8) → `.evoontology` 워크스페이스, `validate_semantics` 통과 | `make_fixture.py` |
| e2e `scripts/lca-e2e-data.sh`: 격리 환경에서 문항마다 `opencode run --agent data-analyst`, 최종 메시지의 `SQL:` 블록(없으면 마지막 db_query 인자)을 **코드가 재실행**해 기대 결과와 비교. D01 결과 일치(tier-1 ≥6/7), D02 토큰(비캐시 입력+출력 ≤10K, 최대 컨텍스트 보고), D03 툴 ≤6, D04 반복 0, D05 쓰기 툴 0, D06 배선(MCP connected + 권한 키), D07 resolve 호출 | |
| doctor D11a~d: 벤더 MCP 응답, sqlite 헬퍼, 픽스처 온톨로지 검증, 프로젝트 설정의 데이터 에이전트/MCP 존재 | `scripts/lca-doctor.sh` |

설계 결정:
- **온톨로지 v0는 코드 생성**(§5.6 "반드시 Gemma로 build"에서 벗어남): 빌드 스킬 3편 ≈ 12K+ 토큰이 26B 세션에 부적합하고, 1차 목표는 "온톨로지 경유 질의 재현"이므로 정답 SQL과 DDL 주석에서 결정적으로 뽑았다. Gemma 빌드/진화는 4단계 야간 배치.
- **`data-analyst`는 `mode: all`**: `opencode run --agent <subagent>`가 subagent를 무시하므로(2단계에서 확인) 직접 호출이 가능해야 e2e를 돌릴 수 있다. main→analyst 자동 위임(`delegate`의 `kind: data`)은 다음 슬라이스.
- **운영 DB 미사용**: 자격이 superuser였고 접속 정보가 코드에 있었다(이후 환경변수 전용으로 정리). `db_query`는 DSN을 설정/로그에 남기지 않고 loopback만 기본 허용.

- 2차 실행: tier-1 7/7, 전체 9/10. HPAI-MAP-003는 1차에 맞았던 문항이 이번엔 `w.report_date < f.report_date`(발생일 당일 제외)로 5가 나왔다.
- 원인 분석(로그의 `resolve_semantics` 응답 비교): 모델이 mention을 "야생조류 검출 건수"로 만들면 용어 `야생조류 검출`의 별칭에 "건수"가 없어 **unresolved**가 되고, 그러면 창 포함 관례(`m-wild`의 BETWEEN)를 보지 못한 채 SQL을 쓴다. mention 표현은 실행마다 달라져 결과가 흔들렸다(같은 조건 2회 재실행 중 1회 실패). EvoOntology의 substring 매칭은 mention 토큰 전부가 용어 이름+별칭 토큰에 포함돼야 하므로 한국어에서는 **셀 수 있는 명사의 단위 표현("건수", "검출 건수")을 별칭에 넣어야** 한다.
- 3차 수정: 제약 `c-window-inclusive`("발생 전 N일 안"은 당일 포함, BETWEEN … AND o.report_date) + 별칭 `건수/검출 건수/야생조류 검출 건수/검출건수` 추가 → HPAI-MAP-003 3회 연속 정답(2.9~4.1K 토큰, 11~14초, 툴 2~4).
- 최종: **10/10**, 질의당 비캐시 입력+출력 2.1~4.6K 토큰(기준 10K), 최대 컨텍스트 ≤3.9K, 7~19초, 쓰기 툴 0, 반복 0, resolve 1회/문항.
- 교훈: 지금까지의 오답 4건은 전부 온톨로지 공백(용어 없음, 별칭 없음, 관례 없음)이거나 픽스처 모호성이었고 db_query/스키마/가드 문제는 없었다. 수정 규칙은 "기대 답을 고치지 말고 용어·별칭·제약을 고친다".

## 4. 확인된 동작 / 주의

- `opencode debug agent`에는 MCP 툴이 나오지 않으므로 e2e 배선 검사는 `opencode mcp list`(connected)와 유효 설정의 permission 키 순서(`evo-semantic_*: deny` 뒤에 allow 2개)로 한다.
- `bun:sqlite`(Bun 1.4.2)는 사용자 정의 함수를 지원하지 않아 sqlite 백엔드를 python 헬퍼 서브프로세스로 구현했다(질의당 ≈50 ms).
- resolve_semantics 응답은 mention 4개에 ≈5K자(≈1.5K 토큰)이며 `guard.trim`이 2.5K 토큰에서 자른다. evidence.result는 생성 시 200자로 잘랐다.
- 스키마 추출기는 운영 Postgres DDL 파일들에서 테이블·컬럼·COMMENT·enum 값·파티션을 뽑는다(운영 스키마용 `data/schema.json` 생성에 사용; 프로젝트 DDL로 검증).

## 5. 사용법

```bash
python3 scripts/fixtures/data-vv/make_fixture.py            # sqlite + schema.json + queries.jsonl + .evoontology(v0)
bash scripts/lca-e2e-data.sh --check                         # 배선 검사(모델 호출 없음)
bash scripts/lca-e2e-data.sh [--tier 2] [--only TEXT-001]    # 실 실행, 문항당 ≈10초
python3 scripts/lca-schema-extract.py path/to/ddl/*.sql --prefix <schema>. -o data/schema.json   # 운영 스키마용
```

프로젝트에서 켜기: `.lca/lca.jsonc`에 `"data": { "backend": "sqlite"|"postgres", "sqlite_path": ..., "schema_file": ..., "evo": { "workspace": ".evoontology" } }`. postgres는 `LCA_PG_DSN` 환경변수(loopback) 필요. TUI에서는 Tab으로 `data-analyst`를 고르거나 `data mode:`로 질문한다.

## 6. 2차 슬라이스 (같은 날): main → data-analyst 위임, 코드측 data_check, data-verifier 게이트

1차 슬라이스의 "남은 것" 중 두 항목을 구현했다.

| 구현 | 내용 |
|---|---|
| `delegate` 태스크 `kind: "data"` | title = 질문, `verify` = 체크 스위트 이름(선택, `default` 내장). 큐가 코드 태스크와 같은 원장/재시도/중단 규칙으로 실행하되 스냅샷·diff·보호파일·게이밍 검사는 건너뛴다(파일을 만지지 않으므로). 스키마 비용 +1 필드(툴 스키마 전체 ≤400 est. 토큰 유지) |
| 파이프라인 (`queue.ts runDataTask`) | `data-analyst` 자식 세션 → 최종 메시지의 `SQL:` 블록 추출(`RESULT:`는 신뢰하지 않음) → **프레임워크가 SQL 재실행 + 체크 스위트 실행**(`data/check.ts`) → `data-verifier` 자식 세션(3문항 답 후 마지막 줄 ACCEPT/REJECT) → 원장(`sql`, `answer`, `verify_result = data_check <suite>`, `review`) + handoff(SQL 코드블록 포함). 체크 실패·SQL 없음·REJECT는 사유를 붙여 1회 재시도; SQL 없이 `ANSWER:`만 오면 "데이터로 답할 수 없음"으로 보고 재시도 없이 blocked; 체크 통과 후 마지막 시도의 REJECT는 advisory(`review_strict`면 실패) — 코드 태스크의 리뷰어 규칙과 동일 |
| `data_check` = 코드 | 설계 §5.3의 `data_check(suite)` **툴**을 검증가 에이전트에게 주지 않고 큐가 실행한다(2단계 교훈: 판정자는 실행하지 않는다, 리뷰어에 bash가 없는 이유와 같음). 스위트 = `data/checks/<name>.json`의 SQL 단언 목록, 답 SQL이 `{answer}` 서브쿼리로 삽입됨(`rows_min/max`, `value`, `value_min/max`, `not_null`, `sql_contains/not_contains`). 내장 `default` = 실행됨·행 있음·NULL 아님. 체크 SQL도 같은 읽기 전용 가드를 지난다 |
| main 프롬프트 규칙 9 (데이터 백엔드가 켜진 프로젝트에서만) | "DB 질문은 기억이나 파일로 답하지 말고 kind data 태스크로 delegate, SQL/ANSWER 줄을 보고" (+≈90 토큰, main ≤1500 유지). `data` 모드 접미도 delegate 경유로 바뀜(main에는 db 툴이 없으므로 이전 접미는 실행 불가능한 지시였음) |
| `data-verifier` | 툴 0개(`steps` 4), 프롬프트를 리뷰어와 같은 "3문항 + 마지막 줄 판정" 형식으로 교체 |
| e2e `--via main` | `opencode run --agent main "data mode: <질문>"` → 원장에서 SQL을 읽어 재실행·비교. D08 원장의 data 태스크 done + 체크 pass, D09 main의 delegate 호출 1회·db 툴 호출 0회. 비교기에 "비교 컬럼이 없으면 행 수만 비교(rows-only)" 폴백 추가 |
| 단위 테스트 | `test/data-task.test.ts` 12개(계약 추출, 체크 스위트, 큐 data 경로 5종, delegate 검증, 프롬프트 배선) → 총 256 |

## 7. 남은 것

- 운영 Postgres 연결 실사용: loopback 터널 + 읽기 전용 계정 발급 전에는 붙이지 않는다.
- 온톨로지의 한국어 매칭은 조사 분리가 없어 별칭 의존적(`runtime.py _tokens`). 질문의 명사 원형 추출을 프롬프트에 의존하고 있음. 4단계 진화 배치가 별칭 공백을 메우는 첫 수단(`docs/lca-stage4-2026-09-23.md`).
- 도메인 체크 스위트는 예시 1개(`data/checks/farm-count.json`)뿐. 운영 질문군이 정해지면 질문 유형별 스위트를 쓴다.
