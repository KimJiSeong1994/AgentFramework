# 로컬 우선 설계 계약

> 출처: [OpenCode 기반 자체 에이전트 프레임워크 심층 검토](../sources/documents-e23212dec8bc6f31aa6120397f75f7dd1d58f0df41dc8275b9b0e3a93df6265a.md) §0, §3. 적용 대상: [otter 프레임워크](../entities/lca-framework.md).

## 계약 (출처가 제시한 세 가지)

1. **정적 프리픽스 불변**: 시스템 프롬프트·툴 목록·thinking 토글은 세션 시작에 확정하고 세션 중 바꾸지 않는다. 모드 지시·todo·리마인더는 마지막 user 메시지 뒤에만 붙인다.
2. **프리픽스 예산**: 툴 포함 8K 토큰 이하, 워커 세션 5K 이하.
3. **코드가 조정한다**: 오케스트레이션·검증·반복 차단은 코드가 맡고, 26B 모델은 워커로 쓴다.

## 왜 필요한가 (관찰, 출처 표기 [검증])

출처는 기존 프레임워크가 "프롬프트 토큰이 싸고, 병렬 슬롯이 무한하며, 모델이 긴 규칙을 잘 따른다"는 전제 위에 있고, 이 머신에서는 셋 다 성립하지 않는다고 본다. 근거로 든 이 머신의 실측은 다음과 같다.

- OMO 프리픽스 31.6K 토큰, 캐시 미스 한 번에 약 72초. 바닐라 build 프리픽스는 6.8K 토큰(13초).
- 한 세션에서 컴팩션 8회가 약 32분, 세션 시간의 약 45%를 차지했다.
- Gemma 26B가 툴 오류 뒤 같은 `write`를 13회 연속 재발행했다. 이것이 코드 측 반복 차단의 근거다.
- 서브에이전트 왕복 후 메인 캐시 복원이 비결정적이었다. 그래서 "복원되지 않는다"고 가정하고 설계한다.
- 26B↔31B 모델 전환에 약 5분이 들어 에이전트별 모델 라우팅을 하지 않는다.

이 수치들은 2026-09-22 시점의 이 머신·설정에서 나온 관측이다. 다른 모델·버전에서도 같다고 일반화하지 않는다.

## 설계 결정으로의 연결

- 모드를 시스템 프롬프트가 아니라 user 메시지 말미 지시로 표현한다(계약 1).
- 스킬 설명을 상시 스키마에 싣는 대신 필요할 때 SKILL 파일을 읽게 한다(계약 2). `framework/README.md`의 `skills.allow` 설명은 스킬 설명 13개가 약 2K 프리픽스 토큰이라고 적는다(이 위키의 등록 출처가 아닌 저장소 문서). 스킬을 추가할 때 이 비용이 늘어난다는 점은 이 계약과 긴장 관계에 있다.
- 동일 호출 반복 차단, 출력 트리밍, 직렬 워커 큐를 코드로 둔다(계약 3).

## 미확정

- 출처는 `NUM_PARALLEL=2` 환경의 MTP 드래프터 동작과 2슬롯 처리량 저하를 검증하지 못했다고 적는다. 이 위키는 이를 확정하지 않는다.
