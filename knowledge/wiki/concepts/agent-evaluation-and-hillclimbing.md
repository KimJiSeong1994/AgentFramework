# 에이전트 평가와 반복 최적화

[글 모음](../entities/claude-dev.md) · [운영](agent-operations-and-economics.md) · [도구 결과 근거](tool-outcome-evidence.md)

방법론 근거: [등록 연구 노트 A03·A05·A06·A09](../sources/documents-42a99b2d70786650607a57589de0e8bfa4f07c5e97e1a485cd9a686b26b02df8.md). 이 페이지의 평가 절차는 문헌 종합이며 실제 평가 캠페인을 실행한 기록이 아니다.

## 먼저 평가기가 무엇을 재는지 확인한다

A03의 핵심은 실제 목표를 대표하는 사례, 풀 수 있는 난도, 개선 여지, 낮은 실행·판정 변동성이다. 쉬운 문제만 만들거나 현재 모델이 실패한 문제만 모으면 각각 포화와 선택 편향이 생긴다. 강한 모델·더 많은 계산이 도움이 되지 않는 경우에도 평가기가 잘못됐다고 단정하지 말고 문제 명세와 판정·환경을 함께 조사한다.

| 점검 | 확인할 것 |
|---|---|
| 대표성 | 실제 업무, 버그, 사람 작성, 합성 사례의 출처와 비율 |
| 명확성 | 전문가가 같은 판정을 내릴 수 있고 검사 조건이 과제에 명시됨 |
| 난도 | 불가능하거나 모호한 문제가 아니라 개선 가능한 여지 |
| 환경 | 이전 파일·git 이력·정답·캐시가 답을 누출하지 않음 |
| 실행 오류 | timeout·API 오류·출력 절단을 모델 오류와 구분 |
| 판정 오류 | 동일 출력의 재채점과 사람의 표본 검토 |

생산 대화를 가져오기 전에 민감정보·동의·보존 조건을 확인한다. 이 저장소의 메타데이터 제한을 우회해 원문 대화를 수집하라는 제안이 아니다.

## 코드 판정부터, 필요한 곳에 모델 판정

A03은 정답 공간이 닫혀 있으면 정확한 값·스키마·테스트 같은 결정적 검사를 우선한다. 정답이 여러 개인 경우에는 검증 가능한 항목으로 rubric을 만들고 별도 모델의 판정과 사람의 교정을 결합한다. 비교 평가에서는 순서를 무작위화하고 어느 쪽이 기준인지 감춘다.

**추가 해석:** 다른 모델을 썼다는 이유만으로 완전히 독립적인 판정은 아니다. 같은 편향·누락을 공유할 수 있으므로 재현 가능한 실패와 인간 표본 검토를 남긴다. 합격률에는 분자·분모·제외·오류·불확실성을 붙인다.

## 안전한 반복 최적화의 계약

A03의 원칙을 정리하면 다음과 같다.

1. 목표와 수정 가능한 표면을 먼저 제한한다. 품질을 유지하며 비용을 줄이는 목표도 가능하다.
2. 기준선을 반복 측정하고 실무적으로 의미 있는 최소 개선보다 잡음이 작은지 확인한다.
3. 사례를 분리하고 정답 접근을 구조적으로 제한한다.
4. 한 번에 하나의 원인 관련 변경을 평가한다. 실패 사례의 문구를 프롬프트에 복사해 외우게 하지 않는다.
5. 회귀와 train만 개선하는 변경을 채택하지 않는다.
6. 정체되면 실패를 분류하고 평가 오류·부족한 반복 수를 먼저 점검한다.
7. 개선 폭과 불확실성을 함께 보고한다. 잡음 범위의 차이를 효과로 주장하지 않는다.

### 원문의 test 사용에 대한 추가 주의

A03의 예시는 test 결과를 라운드별 채택과 최종 버전 선택에 사용한다. 이것은 train과 분리됐더라도 반복적 선택으로부터 완전히 독립적인 최종 시험은 아니다. **이 위키의 제안**은 이를 선택용 validation으로 취급하고 최종 미사용 holdout을 별도로 남기는 것이다. 원문이 이 세 분할을 직접 요구한 것으로 인용하지 않는다.

## 실험실 지표와 사용자 성과

A06은 빠른 실험실 지표가 실제 지연을 따라가는지 검증한 뒤 회귀 가드로 삼았다고 설명한다. A05의 effort 사례도 경계값 검증에 도움이 된 경우이지 모든 문제에서 계산량만 늘리면 해결된다는 증명이 아니다.

따라서 **스킬 호출 → 내용 반환 → 절차 준수 → 소유자 검증 → 사용자 성과**를 서로 다른 층위로 유지한다. 동일한 실행을 중복 표본으로 세거나, 관계없는 시점의 추천과 성공을 연결하지 않는다. [스킬 페이지](agent-skills-and-extensions.md)의 관측 구분과 함께 읽는다.

문헌의 성과와 이 저장소의 관측을 섞지 않기 위해, 먼저 등록돼 있던 두 출처를 원본과 대조했다. 새 운영 트래픽을 만들거나 추가 capture를 수행한 것은 아니다.

- [도구 출처 3aca54](../sources/tool-runs-3aca54aae22acabc4ca432c87fd6c552aa65ef0185ba6aaee37403f8df5f1386.md): 포함 9 / 저장 관측 9. 원본상 `read` 4, `glob` 3, `grep` 2이며 모두 `success / completed`다. 이는 완료 보고 분류이지 결과의 정확도나 업무 성공률이 아니다. 저장 관측을 모두 포함했다는 뜻도 실제 실행 전체가 수집됐다는 보장은 아니다.
- [라우팅 출처 47ed11](../sources/routing-47ed1186900e8c9302e023b319a6a860cb25601234483d37e123829b38a3f7f7.md): 스캔 파일 0, 유효 이벤트 0, bounded scope는 `complete`. 파싱한 범위가 잘리지 않았다는 뜻이지 모든 실제 세션에서 추천이 없었다는 뜻은 아니다. 추천·실행·성공률의 분모가 없으므로 **N/A**다.

두 자료로 스킬 개선 효과·모델 정확도·비용 절감·캐시 성능은 판정할 수 없다. A03·A06의 외부 사례로 빈 로컬 근거를 채우지 않는다. 초기 빈 출처와 이후 출처는 [도구 결과 근거](tool-outcome-evidence.md)에 시간순으로 구분한다.
