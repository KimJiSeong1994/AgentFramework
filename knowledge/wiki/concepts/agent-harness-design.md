# 에이전트 하네스와 도구 설계

[글 모음](../entities/claude-dev.md) · [컨텍스트](agent-context-and-cache.md) · [평가](agent-evaluation-and-hillclimbing.md)

주요 근거: [등록 연구 노트 A07·A10·A13](../sources/documents-42a99b2d70786650607a57589de0e8bfa4f07c5e97e1a485cd9a686b26b02df8.md). 아래의 “설계 제안”은 원문의 사례를 이 위키가 재구성한 것이며 현재 구현 명세가 아니다.

## 모델이 보는 행동 공간

A13은 도구를 기능 목록이 아니라 모델이 보고 선택할 수 있는 행동으로 다룬다. 질문을 ExitPlanTool의 계획 반환에 함께 넣거나 별도의 Markdown 출력 형식으로 파싱하는 방식보다 독립적인 구조화 질문 도구가 안정적이었다는 사례를 든다. 등록 노트의 “Bash에 혼합”은 원문 재대조에서 확인한 오기로, [출처 통합 주석의 정정](../sources/documents-42a99b2d70786650607a57589de0e8bfa4f07c5e97e1a485cd9a686b26b02df8.md)을 따른다. 또한 검색으로 필요한 문맥을 직접 찾게 하고, 별도 가이드 에이전트에서 큰 참고 자료를 소화하는 방식을 설명한다.

**설계 제안:** 도구마다 입력 타입, 결과 의미, 실패, 취소, 부작용을 분명히 한다. 같은 목적의 유사 도구를 늘리기 전에 기존 도구와 파일 기반 참고 자료로 충분한지 확인한다. 발견 가능한 도구라고 해서 실행 권한이 있는 것은 아니다. 모델이 좋아지면 기존 보조 장치도 다시 평가하되, 단일 모델의 사례를 전체 모델 지원 정책으로 일반화하지 않는다.

## 언제 작업을 나누는가

A10은 긴 단일 문맥에서 생기는 문맥 오염, 자기 결과를 선호하는 검토, 목표 이탈을 별도 문맥과 조정으로 완화하려 한다. 다음 여섯 패턴을 소개한다.

| 패턴 | 맞는 문제 | 추가로 확인할 조건 — 위키 해석 |
|---|---|---|
| 분류 후 실행 | 입력 유형에 따라 다른 처리 | 분류 불확실성, 허용된 경로, 잘못된 분류 비용 |
| 병렬 분할 후 종합 | 독립적인 여러 대상 | 파일 소유권, 종합 전 join, 중복 결과 |
| 적대 검토 | 구현과 판정의 시각 분리 | 독립 근거, 재현 절차, 오탐 재검토 |
| 생성 후 필터 | 후보가 많고 선별 기준이 있음 | 기준을 후보 결과에 맞춰 바꾸지 않기 |
| 대진 비교 | 절대 점수보다 상대 비교가 쉬움 | 순서 편향, 비교 비용, 비교 기준 일관성 |
| 종료 조건까지 반복 | 총 작업량을 미리 모름 | 예산·시간·실패 상한과 종료 조건 |

작은 수정에 여섯 패턴을 모두 적용할 이유는 없다. 분할이 독립 문맥이나 병렬성의 이득을 주는지 먼저 판단한다. A10 자체도 토큰 사용 증가와 발전 중인 관행이라는 한계를 밝힌다.

## 완료·중단·재개 계약

A07은 목표뿐 아니라 완료를 확인하는 방법과 사람이 필요한 중단 조건을 함께 쓰도록 권한다. 작업 목록을 파일에 남기고, 자식의 반환값도 근거를 확인한 뒤 받아들인다.

**설계 제안:** 조정 계층은 최소한 다음을 구별해야 한다.

- 작업이 실행 중인 상태와 실행이 끝난 상태.
- 자식이 작업을 마친 것과 소유자가 결과를 검증한 것.
- 검증 실패와 환경·인증·사용자 결정 때문에 막힌 것.
- 재시도 가능한 실패와 이미 완료되어 다시 실행하면 안 되는 것.

자식의 자연어 “완료”를 전체 목표 달성으로 바꾸지 않는다. 목표를 오래 유지하는 능력은 무한 실행 허가가 아니다. 종료 조건과 비용 제한은 모델의 의욕이 아니라 관측 가능한 상태로 판정해야 한다.

## 비신뢰 읽기와 실행의 분리

A10은 외부 티켓·보고서를 읽는 저권한 reader와 실행 권한을 가진 actor를 나누는 격리 패턴을 제시한다. A01의 명령 확인 UI는 권한 시스템의 대체물이 아니라고 명시한다.

**추가 주의:** reader의 요약도 원문에서 유래한 비신뢰 데이터다. 요약했다고 권한 있는 지시로 승격되지 않는다. actor는 정해진 입력 구조·범위·출처를 확인하고 별도 승인 규칙을 적용해야 한다. 동적으로 생성한 조정 코드도 같은 검토 대상이다. 참고: [스킬·확장의 권한 경계](agent-skills-and-extensions.md).

## 이 저장소에 적용해 검토할 질문

[로컬 우선 계약](local-first-contract.md)과 [otter 프레임워크](../entities/lca-framework.md)를 비교 대상으로 삼는다. 이 질문들은 변경 요청이나 구현 완료 주장이 아니다.

1. 모델이 바뀌어도 완료·승인·취소의 판정이 코드에서 일관되는가?
2. 병렬 작업의 반환 근거와 최종 소유자의 결과가 별도로 남는가?
3. 재개 시 이미 완료한 부작용을 반복하지 않는가?
4. 같은 실패가 반복될 때 에이전트 수를 늘리기보다 입력 계약·검증기부터 점검하는가?
5. 사람이 읽는 [검토 산출물](agent-human-review-artifacts.md)에 범위·결과·미확인이 함께 보이는가?
