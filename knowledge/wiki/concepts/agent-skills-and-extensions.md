## 스킬은 작은 지식·실행 패키지다

A09는 스킬을 지침뿐 아니라 참고 문서·스크립트·자료를 담는 폴더로 설명한다. 아홉 용도는 API 참조, 제품 검증, 데이터 분석, 업무 자동화, scaffolding, 품질 검토, CI/CD·배포, runbook, 인프라 운영이다. 이는 용도 분류이지 한 스킬에 모두 넣으라는 뜻이 아니다.

| 설계 항목 | 원문에서 얻는 원칙 | 위키의 검토 질문 |
|---|---|---|
| description | 호출할 상황을 식별하게 작성 | 발동하면 안 되는 가까운 사례도 구분되는가? |
| 본문 | 일반 상식보다 현장의 함정 | 실제 실패를 막는 정보인가, 중복 지침인가? |
| 참고 자료 | 필요한 파일을 단계적으로 읽기 | 관련 파일까지 찾아갈 명확한 안내가 있는가? |
| 코드 | 반복 작업은 재사용 가능한 함수·스크립트 | 입력 검증과 실패 결과를 확인할 수 있는가? |
| 초기 설정 | 설정되지 않은 상태를 명시적으로 처리 | 비밀을 지침에 넣지 않고 안전하게 전달하는가? |
| 상태 | 반복 실행에 필요한 정보만 보존 | 위치·수명·정리·민감정보 기준이 있는가? |
| 배포 | 저장소 공유 또는 선택 설치 | 소유자·버전·의존성·회귀 검증이 명확한가? |

A09의 marketplace는 스킬 간 의존성을 자동으로 해결하는 패키지 관리자와 같지 않다. 다른 스킬의 이름을 적었다고 그 스킬이 설치되거나 허가된 것은 아니다.

## 호출·반환·준수·성과를 구분한다

A09의 사용 기록은 인기 또는 예상보다 낮은 발동을 찾는 신호다. 다음 네 단계는 서로 대체하지 않는다.

1. 호출이 관측됨.
2. 스킬의 내용이 반환됨.
3. 요청한 절차가 수행됨.
4. 업무 결과가 좋아짐.

이 구분은 [도구 결과 근거](tool-outcome-evidence.md)와 일치한다. 절차 준수에는 별도 관측이, 인과적 개선에는 비교 가능한 평가가 필요하다. 원문 대화·도구 본문을 많이 저장한다고 좋은 평가가 되는 것은 아니다. 데이터 최소화와 승인된 보존 경계를 먼저 적용한다.

## Mods: 관찰과 실행 개입의 구분

A01은 이벤트 체인에서 관찰, 재작성, 직접 응답을 구분한다. 관찰 훅은 원래 동작을 통과시키고 결과를 읽지만 재작성이나 거부는 비즈니스 동작을 바꾼다. 같은 플러그인 API에 있다는 이유로 이들의 권한을 동일하게 취급하면 안 된다.

- **재로딩:** 모듈 변수와 호스트의 세션 상태 수명이 다르다. 재등록·재시작 이벤트의 중복 영향을 확인한다.
- **버전:** 글은 Claude Code 2.1.287 이상과 빌드가 생성하는 타입 선언을 기준으로 한다. OpenCode의 훅에 그대로 대응된다고 가정하지 않는다.
- **UI:** 표시 공간이 없거나 다른 UI가 우선하면 양보한다. 화면에 보이지 않는다고 실행이 취소됐다고 가정하지 않는다.
- **명령 가드:** Blast Radius는 문자열 기반 보조 확인이다. 별칭·스크립트·명령 치환을 포괄하는 강제 권한 체계가 아니다.
- **신뢰:** DOM/Node가 없는 모듈 환경이라도 호스트 API 접근은 강력하다. 발행자 신뢰와 코드 검토가 필요하다.

## 이 저장소에 대한 적용 경계

위 내용은 문서 비교이지 스킬·mods 설치, 호스트 교체, 자동 발동, 원문 편집 이력 저장의 승인 근거가 아니다. 특히 Replay Theater의 편집 전후 본문 보존 예시는 이 저장소의 메타데이터 중심 관측 규칙으로 그대로 가져오지 않는다.

개선 후보를 실험하려면 스킬 내용·호출 조건·모델·역할·설정을 구분하고, 먼저 [평가 설계](agent-evaluation-and-hillclimbing.md)를 마련한다. 단지 호출 수가 적다는 이유로 설명을 자극적으로 바꾸거나 권한을 넓히지 않는다.
