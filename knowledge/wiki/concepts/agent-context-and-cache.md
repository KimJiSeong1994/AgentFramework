# 에이전트 컨텍스트와 프롬프트 캐시

근거: [등록 연구 노트 A08·A12, 제품별 보완 A02·A04](../sources/documents-42a99b2d70786650607a57589de0e8bfa4f07c5e97e1a485cd9a686b26b02df8.md).

## 필요한 정보와 항상 싣는 정보를 나눈다

A08은 system prompt·저장소 지침·스킬·요청의 중복과 모순을 줄이고, 자세한 참고 자료는 필요할 때 읽는 방식을 권한다. A13의 검색 도구 설계와 A09의 스킬 폴더 구조도 같은 방향이다.

| 정보 | 배치 제안 — 위키 종합 |
|---|---|
| 제품 역할과 반드시 유지할 경계 | 짧고 일관된 기본 계약 |
| 도구 사용법·상태 타입 | 해당 도구의 스키마와 설명 |
| 저장소 특유의 함정 | 가벼운 저장소 지침과 연결된 참고 문서 |
| 특정 절차·예제·스크립트 | 호출 시 읽는 스킬 패키지 |
| 이번 작업의 목표·검증 조건 | 작업별 명세와 내구 상태 |
| 최근 상태 변화 | 기존 프리픽스를 덮어쓰지 않는 추가 메시지 |

A08의 system prompt 80% 이상 축소는 특정 모델의 내부 코딩 평가에서 보고한 사례다. 이 비율을 다른 모델이나 권한 정책에 그대로 적용하지 않는다. 삭제할 후보는 중복된 행동 유도이지 비밀 보호·승인·데이터 경계가 아니다.

## 캐시는 앞에서부터 같은 부분을 재사용한다

A12가 설명한 기본 순서는 안정적인 system·tools → 프로젝트 맥락 → 세션 맥락 → 누적 메시지다. 앞부분의 시간 문자열, 비결정적 도구 순서, 중간 도구 정의 변경은 뒤쪽 캐시 재사용을 줄일 수 있다.

**설계 제안:** 동일 입력의 직렬화 순서와 스키마를 결정적으로 만들고, 잦은 상태 변화를 뒤에 추가한다. 계획 모드 등 상태 전환을 표현할 때 캐시 안정성과 실제 실행 가드를 분리한다. 도구 정의가 요청에 남아 있다는 사실은 실행 허용을 뜻하지 않는다.

도구 지연 로드는 도구를 매번 제거했다가 재삽입하는 것과 다르다. A12는 안정적인 가벼운 목록을 두고 필요한 정의를 검색해 불러오는 방식을 설명한다. 스킬·자료의 점진 공개는 [스킬·확장](agent-skills-and-extensions.md)에서 다룬다.

## 요약 요청의 재사용과 요약 이후의 캐시는 다르다

A12는 요약할 때 부모의 system·tools·메시지 prefix를 재사용한 fork에 요약 요청만 덧붙여, 요약을 생성하는 요청의 입력 비용을 낮추는 방법을 설명한다. 요약 출력에 필요한 여유 공간도 남겨야 한다.

그러나 요약 후 짧아진 대화는 새 프리픽스다. A04는 요약 생성과 새 캐시 쓰기의 비용, 필요한 세부 정보가 손실될 위험을 함께 설명한다. 따라서 “cache-safe compaction”을 “요약 이후에도 원래 전체 캐시가 그대로 유지됨”으로 해석하면 안 된다.

**설계 제안:** 관련 없는 작업은 분리하고, 긴 작업은 자연스러운 경계에서 필요한 실패·결정·다음 검증 조건을 명시해 요약한다. 종료 직전의 요약이 경제적인지는 남은 턴 수에 달려 있다.

## 제품별 예외와 측정

- A12의 일반 원칙과 A04의 플랫폼별 effort 변경·TTL 설명을 구분한다.
- A02는 top-level effort 변경과 per-message effort 변경의 캐시 영향이 다르다고 설명한다.
- 모델 전환·공급자·호스트 버전이 바뀌면 과거의 캐시 경험을 그대로 가정하지 않는다.
- 캐시 적중률만 높고 불필요한 턴이 늘면 총비용은 줄지 않을 수 있다. 입력·출력·캐시 쓰기·읽기·턴 수·지연을 함께 본다.

위 항목은 현재 API 계약을 독립 확인한 결과가 아니라 각 글의 범위가 다른 설명을 정리한 것이다. 모델·호스트별 실제 측정 없이는 절감률을 약속하지 않는다. [로컬 우선 계약](local-first-contract.md)의 프리픽스·예산 논의와 연결하되, 그 페이지의 과거 실측을 새 제품의 성능 증거로 재사용하지 않는다.
