## A01 — Getting started with Claude Code mods

- 발행일: 2026-10-01. 저자: Addy Osmani.
- 원문: https://claude.dev/blog/getting-started-with-claude-code-mods/
- 분류: 확장 API, 훅 수명주기, 관측과 권한.
- 원문 요지: 플러그인 모듈의 이벤트 체인에서 관찰, 입력 재작성, 직접 응답을 구분한다. Token Weather는 컨텍스트 사용량을 표시하고, Blast Radius는 위험 명령 앞에 확인 UI를 두며, Replay Theater는 편집 이력을 보여준다. 재로딩 때 모듈 변수는 초기화되므로 호스트가 유지하는 상태와 형식 계약을 사용한다. UI 공간이 없으면 다른 표시 위치로 물러나고, 그릴 내용이 없으면 다음 훅에 넘긴다.
- 설계상 중요한 제한: 글은 Claude Code 2.1.287 이상을 전제로 하며 설치된 빌드가 생성하는 타입 선언을 버전별 기준으로 삼는다. 문자열로 명령을 분류하는 확인 UI는 별칭·스크립트·명령 치환을 포괄하지 못하며 권한 시스템을 대체하지 않는다고 명시한다. 모듈 실행 환경에 DOM/Node가 없다는 설명과 별개로 플러그인은 호스트 API를 통해 넓은 접근이 가능하므로 신뢰할 발행자만 설치해야 한다.
- 이 위키의 해석: 이벤트 관찰과 정책 집행을 같은 기능으로 취급하지 말아야 한다. 코드 예제의 편집 전후 본문 저장 방식은 개인정보 금지 범위가 다른 이 저장소에 그대로 도입할 수 없다. 이 글을 읽었다는 이유로 확장 설치·호스트 업그레이드·관측 활성화가 허가되지는 않는다.

## A02 — Building with Claude Sonnet 5.5

- 원문 요지: 명확한 범위와 확인 방법이 있는 반복 작업에는 Sonnet, 장기적인 판단이 어려운 작업에는 Opus를 시작점으로 제시한다. 모델 교체는 이름만 바꾸는 작업이 아니며 thinking, tool choice, content block, computer toolset, advisor, 진행 표시의 계약을 확인하도록 안내한다. 텍스트가 첫 content block이라고 가정하지 않고 종류별로 처리한다. 낮은 effort에서도 실제 변경을 실행하는 검증이 필요하다고 강조한다.
- 제한: 가격·기본 effort·허용 파라미터·캐시 최소 길이·beta 헤더는 글 발행 당시의 제품 설명이다. API와 Claude Code의 기본값도 다르다. top-level effort 변경과 per-message effort 변경의 캐시 영향이 구분된다. 이 조사에서 실제 API 호환성을 검증하지 않았다.
- 이 위키의 해석: 모델·플랫폼·SDK·호스트 버전을 하나의 실험 조건으로 묶어 비교해야 한다. A04의 코드 편집은 Opus에 남기라는 조언과 이 글의 Sonnet 코딩 권고는 보편 규칙으로 합칠 수 없다. 게시 시점·대상 모델·작업 분포가 다르므로 자체 평가로 결정한다.

## A03 — Automating eval design and hillclimbing with Claude

- 발행일: 2026-09-28. 저자: Lance Martin.
- 원문: https://claude.dev/blog/automating-eval-design-and-hillclimbing/
- 분류: 평가 설계, 판정자 교정, 반복 최적화.
- 원문 요지: 평가 입력은 실제 필요한 작업을 대표해야 하며, 풀 수 있지만 아직 어려운 문제가 남아야 한다. 강한 모델과 더 많은 계산이 전혀 도움이 되지 않으면 문제·판정자·실행 환경을 점검한다. 현재 모델의 실패만 모으면 그 모델에 특화된 시험이 된다. 생산 사례, 버그, 사람이 만든 사례, 합성 사례의 출처와 민감정보를 먼저 확인한다.
- 검증 절차: 정답 공간이 좁으면 코드 판정을 우선한다. 열린 결과는 확인 가능한 항목의 rubric, 별도 판정 모델, 비교 순서 무작위화, 사람의 표본 재판정을 사용한다. 같은 결과의 재채점 일관성, API 오류·시간 초과·잘린 출력, 이전 실행의 파일·git 잔여 상태를 별도로 검사한다.
- 최적화 절차: 바꿀 표면과 목표를 제한하고 한 번에 하나의 의미 있는 변경을 평가한다. train과 test를 나누고 정답 접근을 구조적으로 막으며, 개선이 노이즈보다 작으면 반복 수나 사례 수를 늘린다. 점수 정체 때 원인을 분류하고, 회귀 또는 train만 오르는 변경은 되돌린다. 품질이 포화되면 비용·지연을 최적화할 수 있다.
- 이 위키의 해석: 글의 test는 각 라운드 채택과 최종 버전 선택에도 쓰인다. 따라서 반복 선택에서 생기는 누출을 피하려면 최종 미사용 holdout을 별도로 남기는 편이 안전하다. 이것은 원문을 그대로 반복한 권고가 아니라 이 위키의 추가 방법론적 주의다. 호출률 개선은 스킬 준수나 업무 성과 개선의 증명이 아니다.

## A04 — What a task costs on Opus 5.5

- 발행일: 2026-09-25. 저자: Addy Osmani.
- 원문: https://claude.dev/blog/what-a-task-costs-on-opus-5-5/
- 분류: 과업 비용, 캐시, 재시도, 모델 배치.
- 원문 요지: 단가보다 완료까지의 턴·출력·재시도·캐시 사용이 중요하다. 컨텍스트는 매 요청에 다시 전달되며 thinking도 출력 비용에 포함된다. 더 낮은 effort나 싼 모델이 실패와 재작업을 늘리면 총비용이 오를 수 있다. 검증 수단을 주면 더 많은 추론 없이도 잘못된 시도를 조기에 잡는다. 자식 에이전트도 각각 비용을 쓰고 모델 설정을 상속할 수 있다.
- 운영 포인트: 관계없는 일은 세션을 분리하고, 필요한 상태를 명시해 작업 경계에서 요약한다. 모델·도구 목록·system prefix 변화, 캐시 만료, 일부 플랫폼의 effort 변경은 캐시 비용을 바꾼다. compaction 역시 요약 생성과 새 캐시 쓰기 비용이 있으므로 종료 직전이면 손해일 수 있다.
- 제한: 글의 계산기와 여러 토큰 수는 실측이 아니라 예시이고 일부 계산은 cache write를 생략한다. 구독 화면의 금액은 API 청구서와 같지 않다. 플랫폼별 TTL·가격·effort 처리도 다르다. A02와 모델 배치 권고가 다르므로 특정 제품을 영구 기본값으로 지정하지 않는다.
- 이 위키의 해석: 성공 완료 과업당 총비용과 사람의 재검토 비용을 함께 보되, API 비용과 사람 시간을 합치려면 시간 단가를 명시한다. 이 저장소의 메타데이터 관측만으로 토큰 비용이나 인과적 절감을 계산할 수 있다고 주장하지 않는다.

## A05 — Using Claude Code: Spending your effort

- 발행일: 2026-09-25. 저자: Thariq Shihipar.
- 원문: https://claude.dev/blog/spending-your-effort/
- 분류: 계산 예산, 명세, 검증 강도.
- 원문 요지: effort는 단순한 속도 설정이 아니라 탐색·독립 판단·검증에 쓰는 계산량을 조절한다. 모호한 입력에서 높은 effort는 사용자가 정하지 않은 세부 결정을 늘릴 수 있다. 먼저 명세를 분명히 하면 effort 간 결과 차이가 줄어드는 예시를 든다. 빠르게 구현·피드백하고 검증 단계에 더 높은 effort를 배치하는 방식을 소개한다.
- 근거의 범위: 저자의 작은 앱 실험과 Terminal-Bench 3.0 내부 실행 분석이다. 숨은 경계값을 찾는 작업에서는 개선되지만 잘못된 접근 자체를 항상 고치지는 않는다. 모델 실행 시점·네트워크 제한·안전 설정 등이 같지 않고 개별 과업 예시는 소수 반복이므로 보편적 성공률로 옮기지 않는다.
- 이 위키의 해석: 구현과 검증의 예산을 분리하되 낮은 effort를 무검증 면제로 사용하지 않는다. 반복되는 개념 오류는 예산만 올리기 전에 가정·도구·평가기부터 점검한다.

- 이 위키의 해석: 명확한 완료 계약은 무한 실행 명령이 아니다. 사람에게만 가능한 결정과 실행 중인 업무의 상태를 구분하고, 이미 완료한 일을 다시 시작하지 않도록 내구 상태를 사용한다.

## A08 — The new rules of context engineering for Claude 5 generation models

- 발행일: 2026-07-24. 저자: Thariq Shihipar.
- 원문: https://claude.dev/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models/
- 분류: 컨텍스트 설계, 인터페이스, 점진 공개.
- 원문 요지: system prompt·저장소 지침·스킬·사용자 요청이 반복하거나 모순되면 불필요한 판단 비용이 생긴다. 코드 스타일의 세부 금지 목록 대신 주변 코드와 맞추라는 맥락을 주고, 도구 사용법은 매개변수와 상태 타입으로 표현한다. 항상 필요한 정보와 필요할 때 읽을 참고 자료를 나눈다. 저장소 지침은 일반 상식보다 해당 저장소의 함정에 집중한다. 코드·테스트·HTML·rubric도 명세가 될 수 있다.
- 제한: system prompt를 80% 이상 줄여도 코딩 평가 손실을 측정하지 못했다는 주장은 특정 모델과 내부 평가의 결과다. 모든 모델·안전 정책·업무에 동일한 삭제 비율을 적용하는 근거가 아니다.
- 이 위키의 해석: 중복된 행동 유도는 실험으로 줄일 수 있지만 권한·비밀·데이터 경계는 별도의 코드 집행과 정책으로 유지한다. 문서의 간결함과 실행 통제의 약화는 서로 다른 결정이다.

## A09 — Lessons from building Claude Code: How we use skills

- 발행일: 2026-06-03. 저자: Thariq Shihipar.
- 원문: https://claude.dev/blog/lessons-from-building-claude-code-how-we-use-skills/
- 분류: 스킬 설계, 배포, 사용 관측.
- 원문 요지: 스킬은 Markdown 하나가 아니라 지침·참조·스크립트·자료를 담는 패키지다. API 참조, 제품 검증, 데이터 분석, 업무 자동화, scaffolding, 품질 검토, 배포, runbook, 인프라 운영의 아홉 용도를 제시한다. 실제 실패에서 얻은 gotcha를 보강하고, 설명은 내용 요약보다 호출 상황을 식별하게 작성한다. 큰 자료는 필요한 때만 읽고 반복적인 연산은 검증된 코드에 맡긴다.
- 배포·관측: 작은 팀은 저장소, 규모가 커지면 선택 설치형 marketplace를 고려한다. 초기 설정과 지속 상태 위치, 세션 한정 훅을 설계한다. 스킬 간 이름 참조는 가능하지만 의존성 관리가 자동 해결되는 것은 아니다. 호출 관측은 인기·기대보다 적은 발동을 찾는 신호다.
- 이 위키의 해석: 호출 수만으로 절차 준수나 결과 품질을 판정하지 않는다. 실패 사례를 저장할 때 원문 대화·비밀을 통째로 축적하지 않고 프로젝트 보존 정책을 따른다. 자동 발동 권고는 이 저장소의 명시적 호출·승인 경계를 바꾸지 않는다.

## A10 — A harness for every task: dynamic workflows in Claude Code

- 발행일: 2026-06-02. 저자: Thariq Shihipar, Sid Bidasaria.
- 원문: https://claude.dev/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code/
- 분류: 다중 에이전트, 조정 코드, 신뢰 경계.
- 원문 요지: 긴 대화의 문맥 오염·자기 결과 선호·목표 이탈을 줄이기 위해 좁은 목표의 별도 컨텍스트를 조정한다. 분류 후 실행, 병렬 분할 후 종합, 적대 검토, 생성 후 필터, 대진 비교, 종료 조건까지 반복하는 여섯 패턴을 소개한다. 분할 결과는 barrier에서 기다려 구조화해 합치고 자원 집약 명령의 무제한 병렬화를 피한다.

- 이 위키의 해석: 종료 조건·예산·중복 방지·결과 계약은 조정 계층에서 명시해야 한다. reader 요약도 신뢰할 수 없는 데이터이므로 구조 검증과 독립 권한 확인이 필요하다.

## A11 — Using Claude Code: The unreasonable effectiveness of HTML

- 발행일: 2026-05-20. 저자: Thariq Shihipar.

- 분류: 사람이 검토하는 산출물, 명세, 피드백 UI.
- 원문 요지: 긴 결과를 읽기 쉽게 배열하고 비교·주석·시각화를 넣으면 사람이 실제로 검토하기 쉬워진다. 명세, 디자인 실험, diff, 조사 보고서, 특정 데이터 편집기를 HTML로 만드는 예를 든다. 상호작용 결과를 JSON·diff·프롬프트처럼 다시 사용할 수 있는 형태로 내보내는 연결이 중요하다.

- 이 위키의 해석: 읽기 쉬운 UI는 검토를 돕지만 승인 기록이나 검증 증거 자체는 아니다. 활성 콘텐츠·외부 스크립트·민감 데이터 공개를 별도 통제한다. 이 저장소의 기본 위키는 기존 Markdown 규약을 유지한다.

## A12 — Lessons from building Claude Code: Prompt caching is everything

- 발행일: 2026-04-30. 저자: Thariq Shihipar.
- 원문: https://claude.dev/blog/lessons-from-building-claude-code-prompt-caching-is-everything/
- 분류: 프리픽스 안정성, 도구 지연 로드, compaction.
- 원문 요지: 캐시는 요청의 앞부분이 일치해야 재사용되므로 잘 변하지 않는 system·tools를 앞에, 프로젝트 정보·세션 변화·메시지를 뒤에 둔다. 시간·무작위 순서·중간 도구 정의 변경은 캐시를 깨뜨릴 수 있다. 상태 변경은 기존 prefix 수정 대신 새 메시지로 전달하고, plan 전환도 안정된 도구 집합과 상태로 다룬다. 필요한 도구 정의는 검색 후 로드해 초기 문맥을 줄인다.
- 요약·운영: compaction 요청도 기존 도구·프리픽스를 재사용하는 fork로 만들면 불필요한 재처리를 줄일 수 있다. 요약 이후에는 새 대화 프리픽스가 생긴다는 사실과 구분한다. 캐시 적중률을 제품의 지연·비용 관측 대상으로 다룬다.
- 제한: API·호스트별 캐시 계약과 당시 구현의 설명이다. A02·A04의 후속 제품별 예외를 무시하고 모든 설정 변화가 항상 같은 영향을 준다고 일반화하지 않는다.
- 이 위키의 해석: 안전 경계나 권한을 희생해 캐시를 유지하는 것은 목적이 아니다. 순서·스키마 안정성은 결정적 코드로 확보하고 실제 비용·지연으로 효용을 확인한다.

## A13 — Seeing like an agent: how we design tools in Claude Code

- 발행일: 2026-04-10. 저자: Thariq Shihipar.
- 원문: https://claude.dev/blog/seeing-like-an-agent/
- 분류: 도구 인터페이스, 모델의 행동 공간, 탐색.
- 원문 요지: 사람이 편리한 도구 목록보다 모델이 관측하고 선택할 수 있는 행동 공간을 설계해야 한다. 질문을 Bash에 혼합하거나 특수 출력 문자열로 흉내 내는 대신 구조화된 질문 도구를 사용한 사례를 설명한다. 모델 능력이 변하면 Todo 같은 기존 보조 장치도 재검토해야 한다. 코드 검색과 skill을 통해 필요한 정보에 점진 접근하는 방식이 중요하다.
- 제한: 도구의 최적 개수나 형태가 모든 모델·업무에서 같다는 결론이 아니다. 개별 사례는 실제 사용을 살펴보고 반복적으로 조정한 설계 경험이다.
- 이 위키의 해석: 명확한 입력·결과·오류·취소 계약을 가진 작은 행동 단위를 먼저 만들고, 검색 가능성과 권한 집행은 별도로 설계한다. 자동 검색은 자동 실행 승인이 아니다.

## 공통 종합과 보류

1. 검증 가능한 완료 조건 → 좁은 실행 계약 → 필요한 문맥 → 실제 확인 → 사람의 위험 승인이라는 순서로 읽을 수 있다. 이는 13편을 함께 읽은 이 위키의 종합이지 원문 하나의 공식 아키텍처가 아니다.

3. A02와 A04의 모델 선택 조언은 별도로 보존한다. 최신 글을 이유로 이전 글의 관찰을 삭제하거나 로컬 모델 설정을 바꾸지 않는다.
4. A03의 반복 test 사용은 최종 평가의 독립성을 자동 보장하지 않는다. A06의 실험실 지표도 현장 성능을 자동 보장하지 않는다. 둘 다 측정 대상을 실제 목표와 맞추는 문제다.
5. 글의 제품명·가격·성능 수치는 발행일에 묶인 출처 주장으로만 다룬다. 여기서 다룬 모델·mods·beta API가 설치된 OpenCode 호스트에 존재한다고 주장하지 않는다.
6. 이 조사는 문서화다. 모델 교체, 프롬프트·정책 수정, 자동 학습, 새로운 운영 관측 캠페인, 플러그인 설치, 게시·배포는 수행하지 않는다.
